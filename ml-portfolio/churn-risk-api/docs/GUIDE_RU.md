# Разбор проекта для собеседования — Customer Churn

## Задача

Классификация оттока клиентов на открытом **учебном наборе IBM с вымышленными клиентами**. Цель — ранжировать клиентов по вероятности оттока, не утверждая, что алгоритм способен доказать эффективность удерживающей акции.

## Методология

1. Данные разделяются на train (60%), validation (20%) и test (20%) с сохранением долей классов.
2. Исключаем `customerID` и целевой столбец `Churn`; пустые `TotalCharges` при `tenure=0` обрабатываем как нулевые начисления.
3. Преобразования `SimpleImputer`, `StandardScaler`, `OneHotEncoder` обучаются внутри `Pipeline` в каждом fold.
4. Сравниваем Dummy, Logistic Regression, Random Forest, CatBoost по `average_precision` на train-CV.
5. **Только на validation** подбираем порог по гипотетическим издержкам: ложноотрицательный случай — 150, ложноположительный — 25 условных единиц. Это не реальные деньги и не измеренный ROI.
6. Переобучаем модель на train+validation и оцениваем sealed test один раз. Сохраняем модель и публикуем FastAPI `/predict`.

## Вопросы на интервью

- Почему accuracy недостаточно при дисбалансе классов? Важны PR-AUC, recall и precision.
- Чем ROC-AUC отличается от PR-AUC и когда важнее PR-AUC?
- Почему порог выбирается на validation, а не на test? Иначе метрика на тесте окажется оптимистичной.
- Как меняется решение при росте стоимости ложных срабатываний? Порог обычно растёт.
- Почему прогноз риска ухода — не доказательство причинного эффекта удержания? Для оценки эффекта нужна экспериментальная проверка.
- Почему random split недостаточно для настоящего бизнеса? Нужны временная валидация, мониторинг данных и отложенная когорта.
